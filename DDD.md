# Data Design Document (DDD)

How ATS stores its data: entities, tables, columns, constraints and the rules around them.
This is the design the Prisma schema (week 5) will implement; when the schema changes, this file changes in the same commit.

| | |
|---|---|
| **Database** | PostgreSQL 18 (Docker service `db`) |
| **Storage** | Docker volume `alumni-db-data`: kept by `docker compose down`, deleted by `docker compose down -v` |
| **Access** | Prisma 7: schema in `backend/prisma/schema.prisma`, migrations in `backend/prisma/migrations/`. The models in `backend/src/*/*.model.ts` read and write through `PrismaService` |
| **Demo data** | `backend/prisma/seed.ts` builds records with the factories in `backend/prisma/factories.ts`: synthetic Turkish names (fakerTR), e-mails at `example.com` |
| **Status** | All tables below exist in the database (first migration). Five are used by the code (`users`, `announcements`, `job_postings`, `job_applications`, and `alumni_profiles` at registration); the rest are not used yet (week still to be set) and may still change |

## 1. Conventions

| Topic | Decision |
|---|---|
| Table names | plural `snake_case` (`users`, `career_entries`) |
| Primary key | `id`, integer, generated by the database |
| Timestamps | `created_at` (and `updated_at` where a row is edited), type `timestamptz`; the API returns them as ISO strings |
| Enums | fixed lists kept in one place (section 5); a value outside the list is a `400` |
| E-mail | stored lower-case, unique |
| Foreign keys | named `<entity>_id`; what happens on delete is stated per relation |
| Personal data | only what the feature needs (see section 7) |

## 4. Tables

`PK` primary key · `FK` foreign key · `UQ` unique · `NN` not null

### 4.1 `users` *(in code)*

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | integer | PK | |
| `email` | varchar | UQ, NN | lower-case; duplicate → `409` |
| `role` | enum `Role` | NN | `ADMIN`, `STAFF`, `ALUMNI`, `STUDENT` |
| `status` | enum `Status` | NN, default `PENDING` | a new user always starts as `PENDING` |
| `created_at` | timestamptz | NN, default now | |

No password column yet: authentication arrives in week 11.

Rules in code today (`UsersService`):

- `POST` needs `email` and `role`; `status` is not accepted and is always set to `PENDING`.
- `PUT` needs `email`, `role` and `status`; `PATCH` needs at least one of them.
- `id` and `created_at` are read-only; any other field is a `400`.
- `email` is trimmed, lower-cased and must look like an e-mail address; `role` and `status`
  are accepted in any case (`alumni` → `ALUMNI`) and must be a value from section 5.
- Deleting a user deletes their job applications (4.9), alumni profile (4.3) and event
  registrations (4.7): the foreign keys cascade.

#### Roles

Every user has exactly one role. The role says what kind of person the account belongs to and,
from week 11, what the account may do.

| Role | Who | In code today | Planned (week 11 and later) |
|---|---|---|---|
| `ADMIN` | IT or alumni-office administrator | stored only | approves or rejects sign-ups, suspends accounts, manages roles |
| `STAFF` | university staff (career centre, alumni office) | stored; cannot apply to job postings | posts announcements, job postings and events; reads aggregate reports |
| `ALUMNI` | a graduate | may apply to job postings | keeps an alumni profile with career and education history (4.3–4.5), chooses who sees what, offers mentorship, registers for events |
| `STUDENT` | a current student | may apply to job postings | searches the alumni directory, requests mentorship, registers for events |

A visitor without an account is not a role and has no row in `users`; they will see only
aggregate figures.

Role rules:

| Rule | Where |
|---|---|
| Only `ALUMNI` and `STUDENT` may apply to a job posting; other roles → `400` | `JobApplicationsService` (4.9) |
| Only `STUDENT`, `ALUMNI` and `STAFF` may self-register; `ADMIN` → `400` | `RegistrationService` (4.10) |
| Only an `ALUMNI` user has an alumni profile (at most one) | `RegistrationService` (4.10) and the `UQ` on `user_id` (4.3) |
| Only `ADMIN` may change a user's `role` or `status` | planned, week 11; today any client can |
| Only `STAFF` and `ADMIN` may create announcements, job postings and events | planned, week 11; today any client can |

#### Account status

`status` says whether the account may be used. A new account always starts as `PENDING`.

```mermaid
stateDiagram-v2
    [*] --> PENDING : sign-up (POST /api/register or /api/users)
    PENDING --> ACTIVE : admin approves
    PENDING --> REJECTED : admin rejects
    ACTIVE --> SUSPENDED : admin suspends
    SUSPENDED --> ACTIVE : admin restores
```

| Status | Meaning |
|---|---|
| `PENDING` | signed up, waiting for an admin |
| `ACTIVE` | approved; can sign in and use the features of their role |
| `REJECTED` | the sign-up was refused |
| `SUSPENDED` | an approved account that is blocked for now |

Today the diagram is not enforced: `PUT` and `PATCH` accept any status value, and the status
does not yet limit what a user can do (a `PENDING` student can still apply to a job posting).
The transitions and the "only `ACTIVE` users act" rule arrive with sign-in in week 11.

### 4.8 `job_postings` *(in code)*

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | integer | PK | |
| `title` | varchar(120) | NN | required; trimmed, 1–120 characters |
| `company` | varchar | NN | required; trimmed, not empty |
| `location` | varchar | | the city (optional); city level only; empty = not stated |
| `work_type` | enum `WorkType` | NN | `ONSITE`, `HYBRID`, `REMOTE` |
| `employment_type` | enum `EmploymentType` | NN | `FULL_TIME`, `PART_TIME`, `INTERNSHIP`, `CONTRACT` |
| `description` | text | | optional; empty = not stated |
| `apply_url` | varchar | | link or `mailto:`; empty = apply in ATS (`job_applications`) |

| `created_at` | timestamptz | NN, default now | |

Rules: `title` and `company` are required, and `title` is at most 120 characters. The city
(`location`) and `description` are optional; a missing or empty value is stored as empty (`null`).

The list is shown newest first. A posting belongs to no user: users are linked to postings
only through their applications (4.9).

### 4.10 Registration *(in code, no table of its own)*

`POST /api/register` is the route of the sign-up page (`/register`). It writes to `users` and,
for a graduate, to `alumni_profiles`. Rules (`RegistrationService`):

| Field | Rule |
|---|---|
| `email` | required; same rules as 4.1; already used → `409` |
| `role` | required; `STUDENT`, `ALUMNI` or `STAFF`. `ADMIN` cannot self-register → `400` |
| `acceptPrivacy` | must be `true` (the privacy notice is accepted); not stored |
| `fullName`, `graduationYear`, `city` | for `ALUMNI` only, see 4.3 (`city` optional); sent with another role → `400` |

The new account is always `PENDING`. Any other field is a `400`. If two requests send the same
e-mail at the same moment, the `UNIQUE` constraint stops the second one, which gets `409`.
No password yet: sign-in arrives in week 11.

## 6. Where each rule lives

| Rule | Enforced by |
|---|---|
| Required fields, length limits, enum values | service (`400`) |
| Missing record | service (`404`), the model only returns `undefined` or `false` |
| Duplicate e-mail / registration / application | service checks first (`409`); a database `UNIQUE` constraint is the safety net |
| Row references that must exist | database foreign keys |

## 7. Privacy (KVKK)

Not stored, by design: national ID number, birth date, grades, home address.
Location is city level. Demo and seed data are synthetic.

## 8. Open points

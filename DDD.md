# Data Design Document (DDD)

How ATS stores its data: entities, tables, columns, constraints and the rules around them.
This is the design the Prisma schema (week 5) will implement; when the schema changes, this file changes in the same commit.

| | |
|---|---|
| **Database** | PostgreSQL 18 (Docker service `db`) |
| **Storage** | Docker volume `alumni-db-data`: kept by `docker compose down`, deleted by `docker compose down -v` |
| **Access** | Prisma 7: schema in `backend/prisma/schema.prisma`, migrations in `backend/prisma/migrations/`. The models in `backend/src/*/*.model.ts` read and write through `PrismaService` |
| **Demo data** | `backend/prisma/seed.ts` builds records with the factories in `backend/prisma/factories.ts`: synthetic Turkish names (fakerTR), e-mails at `example.com` |
| **Status** | All tables below exist in the database (created by the migrations). Six are used by the code (`users`, `announcements`, `job_postings`, `job_applications`, `sessions`, and `alumni_profiles` at registration); the rest are not used yet (week still to be set) and may still change |

## 1. Conventions

| Topic | Decision |
|---|---|
| Table names | plural `snake_case` (`users`, `career_entries`) |
| Primary key | `id`, integer, generated by the database |
| Timestamps | `created_at` (and `updated_at` where a row is edited), type `timestamptz`; the API returns them as ISO strings |
| Enums | fixed lists kept in one place (section 5); a value outside the list is a `400` |
| E-mail | stored lower-case, unique |
| Foreign keys | named `<entity>_id`; what happens on delete is stated per relation |
| Personal data | only what the feature needs (see section 7) |

## 4. Tables

`PK` primary key · `FK` foreign key · `UQ` unique · `NN` not null

### 4.1 `users` *(in code)*

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | integer | PK | |
| `email` | varchar | UQ, NN | lower-case; duplicate → `409` |
| `role` | enum `Role` | NN | `ADMIN`, `STAFF`, `ALUMNI`, `STUDENT` |
| `status` | enum `Status` | NN, default `PENDING` | a new user always starts as `PENDING` |
| `password_hash` | text | | `scrypt$<salt>$<hash>`, set at registration (4.10); empty = cannot log in. Never returned by the API |
| `created_at` | timestamptz | NN, default now | |

Users created through `POST /api/users` (the admin CRUD) have no password and cannot log in.

Rules in code today (`UsersService`):

- `POST` needs `email` and `role`; `status` is not accepted and is always set to `PENDING`.
- `PUT` needs `email`, `role` and `status`; `PATCH` needs at least one of them.
- `id` and `created_at` are read-only; any other field is a `400`.
- `email` is trimmed, lower-cased and must look like an e-mail address; `role` and `status`
  are accepted in any case (`alumni` → `ALUMNI`) and must be a value from section 5.
- Deleting a user deletes their job applications (4.9), alumni profile (4.3) and event
  registrations (4.7): the foreign keys cascade.

#### Roles

Every user has exactly one role. The role says what kind of person the account belongs to and,
from week 11, what the account may do.

| Role | Who | In code today | Planned (week 11 and later) |
|---|---|---|---|
| `ADMIN` | IT or alumni-office administrator | the admin panel `/admin` (task 5): approves or rejects sign-ups, changes any role and status, deletes users; the only role that may change users | reports, audit of changes |
| `STAFF` | university staff (career centre, alumni office) | stored; cannot apply to job postings | posts announcements, job postings and events; reads aggregate reports |
| `ALUMNI` | a graduate | may apply to job postings | keeps an alumni profile with career and education history (4.3–4.5), chooses who sees what, offers mentorship, registers for events |
| `STUDENT` | a current student | may apply to job postings | searches the alumni directory, requests mentorship, registers for events |

A visitor without an account is not a role and has no row in `users`; they will see only
aggregate figures.

Role rules:

| Rule | Where |
|---|---|
| Only `ALUMNI` and `STUDENT` may apply to a job posting; other roles → `400` | `JobApplicationsService` (4.9) |
| Only `STUDENT`, `ALUMNI` and `STAFF` may self-register; `ADMIN` → `400` | `RegistrationService` (4.10) |
| Only an `ALUMNI` user has an alumni profile (at most one) | `RegistrationService` (4.10) and the `UQ` on `user_id` (4.3) |
| Only `ADMIN` may create, change or delete a user (including `role` and `status`) and read `/api/admin`; others → `403` | `AuthMiddleware` (4.12) |
| An admin cannot change their own role, deactivate their own account or delete it → `400` | `UsersService` (4.1) |
| Only `STAFF` and `ADMIN` may create announcements, job postings and events | planned, week 11; today any logged-in user can |

#### Account status

`status` says whether the account may be used. A new account always starts as `PENDING`.

```mermaid
stateDiagram-v2
    [*] --> PENDING : sign-up (POST /api/register or /api/users)
    PENDING --> ACTIVE : admin approves
    PENDING --> REJECTED : admin rejects
    ACTIVE --> SUSPENDED : admin suspends
    SUSPENDED --> ACTIVE : admin restores
```

| Status | Meaning |
|---|---|
| `PENDING` | signed up, waiting for an admin |
| `ACTIVE` | approved; can sign in and use the features of their role |
| `REJECTED` | the sign-up was refused |
| `SUSPENDED` | an approved account that is blocked for now |

Only an `ACTIVE` account can log in (4.11). Apart from that, the diagram is not enforced yet:
`PUT` and `PATCH` accept any status value, and a `PENDING` student can still apply to a job
posting. The transitions and role checks on the other routes arrive in week 11.

### 4.10 Registration *(in code, no table of its own)*

`POST /api/register` is the route of the sign-up page (`/register`). It writes to `users` and,
for a graduate, to `alumni_profiles`. Rules (`RegistrationService`):

| Field | Rule |
|---|---|
| `email` | required; same rules as 4.1; already used → `409` |
| `role` | required; `STUDENT`, `ALUMNI` or `STAFF`. `ADMIN` cannot self-register → `400` |
| `acceptPrivacy` | must be `true` (the privacy notice is accepted); not stored |
| `password` | required; 8–128 characters; stored only as `password_hash` (4.1) |
| `fullName`, `graduationYear`, `city` | for `ALUMNI` only, see 4.3 (`city` optional); sent with another role → `400` |

The new account is always `PENDING`. Any other field is a `400`. If two requests send the same
e-mail at the same moment, the `UNIQUE` constraint stops the second one, which gets `409`.

### 4.11 `sessions` *(in code, week 9)*

One row per login. The browser keeps a random token in the `ats_session` cookie (HttpOnly,
SameSite=Lax, 7 days); the table stores only the token's SHA-256 hash.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | integer | PK | |
| `token_hash` | text | UQ, NN | SHA-256 of the cookie token, hex |
| `user_id` | integer | FK → `users.id`, NN | delete the user → delete their sessions |
| `created_at` | timestamptz | NN, default now | |
| `expires_at` | timestamptz | NN | 7 days after login; an expired session is deleted when it is next read |

Rules (`AuthService`, routes under `/api/auth`):

| Route | Rule |
|---|---|
| `POST /api/auth/login` | `email` and `password` required (`400`). Unknown e-mail, no password or wrong password → `401` with one message for all three. Account not `ACTIVE` → `403` with its status. Success → `200`, the user and a new cookie |
| `POST /api/auth/logout` | deletes the session of the cookie (if any) and clears the cookie → `204` |
| `GET /api/auth/me` | `200` with `{ user }`, or `{ user: null }` when nobody is logged in, the session expired or the account is no longer `ACTIVE` |

### 4.12 Who may use which route *(auth middleware, week 9)*

`AuthMiddleware` runs on every request. It reads the `ats_session` cookie and puts the
logged-in user on the request (`req.user`, `null` for a visitor). The table below is
`backend/src/auth/access-rules.ts`. Without a login, a protected API route answers `401`
and a protected page redirects to `/login?next=<page>`.

| | Without login | Login required | `ADMIN` only (`403` for other roles) |
|---|---|---|---|
| JSON API | `GET` announcements and job postings (list and one), `GET /api/health`, Swagger, `POST /api/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me` | everything else: every `POST`/`PUT`/`PATCH`/`DELETE`, users, job applications (also under a posting or a user), `GET /api/account` | `GET /api/admin/summary`; `POST`, `PUT`, `PATCH`, `DELETE` on `/api/users` |
| Pages | `/`, `/about`, announcements and job postings (list and one), `/register`, `/login`, `/404` | `/platform` (the workspace), `/users…`, `/job-applications…`, `/admin`, `/account`, every `…/create` and `…/edit` page, `/job-postings/:id/applications` | (`/admin` shows "Only admins" to other roles: its data is `ADMIN` only) |

Apart from the `ADMIN` column, any logged-in user passes; other role checks come in week 11. An unknown `/api` path
answers `401` to a visitor and `404` after login.

The first `ACTIVE` account is the admin from `.env` (`ADMIN_EMAIL`, `ADMIN_PASSWORD`),
created on startup if that e-mail has no account yet. It approves new accounts by setting
their status to `ACTIVE`.

### 4.13 Menu by role *(task 6, week 9, no table of its own)*

`GET /api/auth/me` returns `{ user, menu }`. `menu` is the header menu for the
role, built by `backend/src/auth/navigation.ts`; the landing and the workspace draw
their menu from it (`backend/public/account.js`).

| Menu link | Visitor | `STUDENT` | `ALUMNI` | `STAFF` | `ADMIN` |
|---|:---:|:---:|:---:|:---:|:---:|
| Home, Opportunities, Announcements, About | ✓ | ✓ | ✓ | ✓ | ✓ |
| Workspace (`/platform`; a visitor is sent to `/login`) | | ✓ | ✓ | ✓ | ✓ |
| Applications (`/job-applications`) | | ✓ | ✓ | ✓ | ✓ |

The ☰ button at the right of the header opens one panel for the account and the settings:

| ☰ panel row | Visitor | Logged in | `ADMIN` |
|---|:---:|:---:|:---:|
| Logged in as (e-mail and role) | | ✓ | ✓ |
| My account (`/account`, 4.14) | | ✓ | ✓ |
| Admin panel (`/admin`), with the number waiting for approval | | | ✓ |
| Log in, Register | ✓ | | |
| Settings: language (Türkçe / English), theme (light / dark) | ✓ | ✓ | ✓ |
| Log out | | ✓ | ✓ |

Below 1200px the menu links move into the same panel, so ☰ is the only menu button.
An `ADMIN` also keeps a burgundy **Admin** button with a shield and the count in the header
(hidden on phones, where the panel row is enough); the user list opens from the admin panel.
After login, an `ADMIN` starts on `/admin`, everyone else on `/platform` (unless `?next=` names a page).

The menu only hides links. Access is still decided by `AuthMiddleware` (4.12):
a user who types `/users` gets the page if their login allows it.

### 4.14 My account *(task 7, week 9, no table of its own)*

`/account` is the logged-in user's own page. Its data comes from `GET /api/account`
(`backend/src/account/`), which has no id in the URL: it always reads `req.user`,
so nobody can open another user's page through it. Without a login → `401`
(the page redirects to `/login`).

`GET /api/account` returns `{ user, alumniProfile, applications }`; a section the
role does not have is `null`.

| Section | `STUDENT` | `ALUMNI` | `STAFF` | `ADMIN` | Data |
|---|:---:|:---:|:---:|:---:|---|
| Account: e-mail, role, status, member since | ✓ | ✓ | ✓ | ✓ | `users` (4.1) |
| Alumni profile: full name, graduation year, city | | ✓ | | | `alumni_profiles` (4.3) |
| My applications, with the posting's title and company | ✓ | ✓ | | | `job_applications` → `job_postings` (4.9) |
| Shortcuts: new announcement, new job posting | | | ✓ | | links only |
| Shortcut: admin panel | | | | ✓ | link only |

The roles that see "My applications" are the roles that may apply (4.9).

## 6. Where each rule lives

| Rule | Enforced by |
|---|---|
| Required fields, length limits, enum values | service (`400`) |
| Missing record | service (`404`), the model only returns `undefined` or `false` |
| Duplicate e-mail / registration / application | service checks first (`409`); a database `UNIQUE` constraint is the safety net |
| Row references that must exist | database foreign keys |

## 7. Privacy (KVKK)

Not stored, by design: national ID number, birth date, grades, home address.
Location is city level. Demo and seed data are synthetic.
